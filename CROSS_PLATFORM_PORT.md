# Порт Meeting Summarizer на macOS и Linux — что для этого нужно

> **Язык:** внутренний исследовательский документ, только русский — как
> `PROJECT_OVERVIEW.md` и `MIC_RECORDER_VS_MEETING_SUMMARIZER.md`.
>
> **Дата:** 2026-08-21. **Версия проекта на момент разбора:** 1.3.0.
>
> **Метод:** это не оценка «на глаз». Каждый пункт получен вычиткой кода —
> поиском по `msvcrt|winreg|taskkill|nvidia-smi|.exe|STARTUPINFO|sys.platform`
> и чтением найденного. Где вывод основан на документации пакета, это указано.

---

## 0. Главный вывод

**Ядро проекта уже почти переносимо, и это не случайность.** Вся тяжёлая логика —
распознавание, ИИ, RAG, экспорт, оба фронтенда — написана на переносимом Python и
Qt. Платформа зашита ровно в трёх местах: **как запускается процесс**, **как
находятся бинарники** и **как раздаётся сборка**.

| Слой | Готовность к переносу | Что мешает |
|---|---|---|
| `backend/processing/*` (движки, VAD, аудио) | **высокая** | ничего; всё через ffmpeg и pip-пакеты |
| `backend/ai_client.py`, `rag.py`, `mcp_server.py` | **высокая** | одна ветка PowerShell для агента-CLI |
| `desktop/app/core`, `ui`, `backend` (адаптеры) | **высокая** | `STARTUPINFO`/`CREATE_NO_WINDOW`, `nvidia-smi`, захват системного звука |
| `server/` (FastAPI + веб) | **полная** | ничего платформенного не найдено |
| `backend/gpu_handoff.py`, `local_ai.py` | **низкая** | `taskkill`, `netstat`, только Windows-сборки llama.cpp |
| `desktop/packaging/*`, `INSTALL.bat`, `RUN.bat` | **нулевая** | вся раздача построена вокруг `.bat` и встроенного `python.exe` |

Оценка объёма: **основная работа не в коде, а в упаковке**. Самого кода править
немного, и почти всё правится «добавить ветку», а не «переписать модуль».

## 1. Что уже переносимо — и почему это важно знать заранее

Чтобы не тратить время на то, что и так работает:

- **`atomic_io.file_lock` уже кроссплатформенный.** Есть обе ветки: `msvcrt` на
  Windows и `fcntl.flock` на остальных. Ничего делать не нужно.
- **`paths.py` уже деградирует правильно.** `python_executable()` ищет
  `backend/python/python.exe`, а если его нет — возвращает `sys.executable`.
  `_ffmpeg_tool()` ищет `backend/FFmpeg/ffmpeg.exe`, а иначе `shutil.which(name)`.
  То есть на Linux/macOS проект уже сейчас найдёт системные python и ffmpeg.
  **Но** оба ищут имена с `.exe` — на POSIX условие просто не сработает и сразу
  уйдёт в fallback. Это работает, но по случайности, а не по замыслу: правильнее
  выбирать имя по платформе.
- **Все движки распознавания есть под macOS и Linux.** `faster-whisper`,
  `ctranslate2`, `openai-whisper`, `vosk`, `sherpa-onnx`, `onnxruntime`,
  `pywhispercpp` публикуют колёса под обе платформы (macOS — включая arm64).
- **Qt/PySide6** — сам по себе кроссплатформенный, включая `QAudioSource`,
  на котором держится запись с микрофона.
- **Веб-кабинет** (`server/`) переносится без единой правки: FastAPI, uvicorn,
  SQLite, статика.

## 2. Что придётся править в коде

### 2.1 Скрытие консольного окна — 4 файла, механическая правка

`subprocess.STARTUPINFO` и `creationflags=CREATE_NO_WINDOW` существуют только на
Windows. Встречаются в:

- `desktop/app/backend/media.py` (нарезка ffmpeg),
- `desktop/app/core/metrics.py` (вызов `nvidia-smi`),
- `backend/gpu_handoff.py`,
- `backend/local_ai.py`.

В `media.py` и `metrics.py` уже есть проверка `hasattr(subprocess, "STARTUPINFO")`,
то есть на POSIX они вернут `None` — но `creationflags=` передаётся всё равно, а
на POSIX это **невалидный аргумент**. Нужно собирать kwargs условно:

```python
_WIN = os.name == "nt"
_popen_kwargs = ({"creationflags": _CREATE_NO_WINDOW,
                  "startupinfo": _hidden_startupinfo()} if _WIN else {})
```

Одна общая функция в `desktop/app/backend/command.py` или в новом
`core/platform.py`, и все четыре места её зовут. Это правка на час.

### 2.2 GPU-метрики и hand-off — самое неприятное место

`core/metrics.py` и `backend/local_ai.py` определяют видеокарту через `nvidia-smi`.
На Linux с NVIDIA это работает как есть. На macOS **NVIDIA не бывает** — там
Apple Silicon (Metal/MPS) или AMD, и `nvidia-smi` не существует. Сейчас код на это
реагирует правильно (`shutil.which` вернёт `None` → «GPU не обнаружен»), то есть
не падает, но и не показывает ничего полезного на машине, где GPU есть.

`backend/gpu_handoff.py` завязан жёстче: `taskkill /F /PID` и разбор вывода
`netstat` для поиска слушателя порта. Оба нужно заменить:

| Что делает сейчас | Windows | POSIX |
|---|---|---|
| убить процесс по PID | `taskkill /F /PID` | `os.kill(pid, SIGTERM)` → `SIGKILL` |
| найти слушателя порта | `netstat -ano` | `psutil.net_connections()` — **psutil уже в зависимостях**, и он кроссплатформенный |
| запустить отвязанный процесс | `DETACHED_PROCESS`/`CREATE_NEW_PROCESS_GROUP` | `start_new_session=True` |

`psutil` здесь снимает почти всю разницу: его стоит использовать и на Windows,
избавившись от разбора текстового вывода `netstat` вообще.

**Замечание про смысл фичи.** GPU hand-off существует, потому что на одной NVIDIA
локальная LLM не оставляет места движку распознавания. На Apple Silicon память
единая, и вся конструкция там не нужна — правильнее не «портировать», а
**отключать** её на macOS с честной подписью в настройках.

### 2.3 Встроенный локальный ИИ — переписывать выбор сборки

`backend/local_ai.py` скачивает релиз llama.cpp и ищет строго:

```python
order = ["bin-win-cuda-12.4-x64", "bin-win-cuda", "bin-win-cpu-x64"]
...
ENGINE_DIR / "llama-server.exe"
```

Для порта нужна таблица «платформа → имя ассета»:

| Платформа | Ассет llama.cpp | Бинарник |
|---|---|---|
| Windows + CUDA | `bin-win-cuda-12.4-x64` | `llama-server.exe` |
| Windows CPU | `bin-win-cpu-x64` | `llama-server.exe` |
| macOS arm64 | `bin-macos-arm64` (Metal) | `llama-server` |
| Linux x64 | `bin-ubuntu-x64` | `llama-server` |

Плюс `chmod +x` после распаковки — на POSIX архив не несёт бит исполняемости
надёжно. Работы примерно на полдня, и она изолирована в одном модуле.

### 2.4 Агент-CLI: одна ветка PowerShell

`ai_client.py` для провайдера `agent` разбирает суффикс команды: `.cmd`/`.bat`
отклоняются, `.ps1` запускается через `powershell.exe`. На POSIX этих суффиксов не
бывает — ветка просто не сработает, но стоит добавить симметричную поддержку
`.sh` и вызова через `/bin/sh`, иначе агент-CLI на Mac будет работать только для
бинарников в PATH.

### 2.5 Захват системного звука — единственное, что реально придётся писать заново

Это самая интересная часть, потому что фича новая (1.3.0) и завязана на
платформенный API.

| Платформа | Что доступно | Статус |
|---|---|---|
| **Windows** | WASAPI loopback через `soundcard` | **работает** (сделано в 1.3.0) |
| **Linux** | PulseAudio/PipeWire **monitor-источники** | `soundcard` их поддерживает: `all_microphones(include_loopback=True)` возвращает мониторы. Скорее всего заработает почти сразу — но проверять надо на живой системе, потому что имя монитора не всегда совпадает с именем sink'а |
| **macOS** | **ничего** через `soundcard` | В самом пакете написано прямым текстом: `# macOS does not support loopback recording functionality` — и вызов с `include_loopback=True` выдаёт предупреждение и возвращает обычные микрофоны |

Для macOS вариантов три:

1. **Виртуальное устройство** (BlackHole, 2 канала — бесплатное, MIT). Пользователь
   ставит его один раз и создаёт Multi-Output Device. Тогда `soundcard` видит
   BlackHole как обычный микрофон и **весь наш код работает без изменений** — от
   него требуется только уметь выбрать устройство захвата для второго канала.
   Это самый дешёвый путь: правок в коде почти нет, есть инструкция.
2. **ScreenCaptureKit** (macOS 13+) — правильный системный способ, тот самый,
   которым пользуется Mic Recorder через Chromium. Из Python доступен через
   `pyobjc` + `ScreenCaptureKit`, но это заметный кусок работы и своя ветка кода.
3. **Ничего не делать**: на macOS писать только микрофон и честно об этом
   сообщать — ровно так, как сейчас ведёт себя код, когда loopback недоступен
   (`loopback.probe()` возвращает причину, а UI её показывает).

**Рекомендация:** сразу сделать (1) + (3) — то есть добавить в настройки выбор
устройства для второго канала и документировать BlackHole; (2) отложить.
Архитектурно мы к этому готовы: `SystemAudioCapture` уже изолирован в
`core/loopback.py` и уже умеет отвечать «недоступно и вот почему».

## 3. Что придётся строить заново: раздача

Здесь кода мало, а работы много — потому что вся текущая раздача построена вокруг
двух допущений: «есть `.bat`» и «Python можно положить в папку».

### 3.1 Лаунчеры

`RUN.bat`, `SERVER.bat`, `INSTALL.bat` нужно продублировать как `run.sh`,
`server.sh`, `install.sh`. Логика внутри та же (найти интерпретатор: встроенный →
записанный установщиком → PATH), и `_selftest_build_composition.py` придётся
научить проверять обе тройки.

### 3.2 Встроенный Python

Windows-сборка **full** несёт `backend/python` — embeddable-дистрибутив Python,
которого для macOS и Linux просто не существует в таком виде. Варианты:

| Подход | Плюсы | Минусы |
|---|---|---|
| **python-build-standalone** (Astral) | готовые релокатируемые сборки CPython 3.11 под macOS arm64/x64 и Linux x64 | ещё один внешний источник, лицензионные заметки |
| **uv** как установщик | быстро, ставит и Python, и зависимости | требует интернета при установке |
| **Только `min`-раздача** на POSIX | ничего не надо изобретать | у пользователя должен быть Python 3.11 — на macOS это `brew install python@3.11` |

**Рекомендация:** для первой итерации выпускать на macOS/Linux **только `min`** и
опираться на системный Python. `full` — отдельная задача, и она не блокирует
коллег, которым нужно «просто работать».

### 3.3 Torch и движки

Windows-манифест закрепляет `torch==2.6.0+cu124`. Для порта нужны три профиля:

| Профиль | Индекс pip | Кому |
|---|---|---|
| Windows/Linux + NVIDIA | `download.pytorch.org/whl/cu124` | как сейчас |
| Linux без GPU | `.../whl/cpu` | серверы |
| **macOS** | обычный PyPI (`torch==2.6.0`) | там колёса уже с поддержкой MPS |

`installer.py` уже умеет выбирать индекс (`torch_cuda_plan` / `torch_cpu_plan` —
это покрыто тестами), так что добавляется третья ветка, а не новая механика.

**Отдельно про macOS:** `numpy<2.0` — это ограничение стека whisper/ctranslate2, и
на macOS arm64 колёса `numpy 1.26` есть, так что запрет не мешает.

### 3.4 Упаковка десктопа

Сейчас раздача — zip с исходниками. На macOS этого мало: приложение без `.app`
неудобно, а без подписи (хотя бы ad-hoc) на Apple Silicon просто не запустится.
Нужен `py2app`/PyInstaller + `codesign`, и это, как и в случае Mic Recorder,
**делается только на macOS**.

## 4. Порядок работ, который я бы предложил

Разбито так, чтобы каждый этап давал коллегам что-то работающее.

| Этап | Что даёт | Оценка |
|---|---|---|
| **1. Кроссплатформенный запуск из клона** — правки 2.1, 2.2, 2.4, `paths.py` по платформе, `run.sh`/`server.sh` | Коллега на Mac/Linux клонирует репозиторий, ставит зависимости и работает. Веб-кабинет — сразу и полностью | 2–3 дня |
| **2. Linux: системный звук и live** — проверить `soundcard` на PulseAudio/PipeWire, поправить резолв монитора | Полный паритет с Windows на Linux | 1 день + прогон на реальной машине |
| **3. macOS: второй канал через выбор устройства** + инструкция по BlackHole | Live-режим на Mac с обоими сторонами разговора | 1–2 дня |
| **4. `install.sh` и `min`-раздача под POSIX** | Установка без git и без ручного pip | 2 дня |
| **5. Локальный ИИ и GPU hand-off по платформам** | Встроенная модель на Mac/Linux | 2–3 дня |
| **6. `.app` + `.dmg`, пакеты для Linux** | Обычная установка вместо архива | отдельная задача, нужен Mac |

Этапы 1–3 закрывают то, ради чего просили коллеги. 4–6 — это уже про удобство
раздачи.

## 5. Чем проверять

В хозяйстве уже есть три виртуалки (Windows 11, Ubuntu, macOS 15.1) — это ровно
тот стенд, который для такой работы и нужен. Важные оговорки:

- **macOS в VMware — это x86-64.** Проверить на нём можно всё, кроме поведения на
  Apple Silicon: там другая архитектура колёс (`arm64`), другой torch (MPS) и
  обязательная подпись бинарников. То есть VM закрывает логику, но не закрывает
  вопрос «запустится ли у коллеги на M-процессоре».
- **Захват системного звука в VM ненадёжен** — виртуальный аудиодрайвер ведёт себя
  не как настоящий. Отрицательный результат в VM не будет доказательством.
- Набор автотестов (53 раннера) почти весь платформонезависим и должен зелёным
  прогоняться на Linux сразу после этапа 1 — это лучший первый индикатор.
