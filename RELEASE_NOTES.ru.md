# Meeting Summarizer 1.3.0

[English](https://github.com/john7ross/meeting-summarizer/blob/main/RELEASE_NOTES.md) · **Русский**

Локальный инструмент: из записи встречи делает структурированное **саммари** и подробный
**анализ**. Транскрибация → саммари → анализ из 11 фич → экспорт. Всё может работать на вашей
машине, офлайн; облачные AI-провайдеры — по желанию.

Второй релиз. Новое: **live-режим** — захват системного звука, live-транскрибация и live-саммари прямо во время встречи. Всё из 1.2.1 сохранено без изменений.

## Чем min отличается от full и что выбрать

**Обе сборки умеют одно и то же.** Это не «lite» и «pro»: код в них побайтово одинаковый — все
7 движков, все 11 фич анализа, оба фронтенда, в каждой. Отличается только то, что уже лежит
внутри архива.

Сравните списки файлов — всё просто: **min строго вложена в full плюс `INSTALL.bat`**.
full дополнительно везёт встроенный Python со всеми пакетами и тяжёлые модели (большие Vosk ru/en,
sherpa-onnx, FunASR, medium-модели Whisper). Всё остальное совпадает — включая маленькие Vosk
ru/en и офлайновые модели разделения по спикерам, которые едут в **обеих**, так что min
транскрибирует офлайн сразу из коробки.

Ни одна из сборок не везёт веса модели эмбеддингов для базы знаний — они скачиваются при первом
обращении.

**Можно ли из min сделать full?** Функционально — да. Отметьте все движки в `INSTALL.bat`, и
установщик предложит 25 моделей; все 10 из набора full среди них, ничего не пропущено. Так что min
доводится до полного паритета по возможностям.

**Структурно — нет, и разница здесь практическая.** Установщик кладёт пакеты в **ваш** Python
(тот, что записан в `config/interpreter.txt`), а не в `backend/python`. Отсюда:

| | min | full |
|---|---|---|
| Куда ложатся зависимости | в ваш Python, на этой машине | в изолированный `backend/python` внутри папки |
| Переносимость | привязана к конкретной установке Python на конкретной машине | скопируйте папку на флешку и запустите на машине без интернета и без Python |
| Нужен ли интернет для установки | да (пакеты и модели скачиваются) | нет |
| Размер загрузки | 330 МиБ плюс то, что добавите | 12,35 ГиБ сразу |
| Добавить что-то потом | `INSTALL.bat` остаётся в папке — запустите ещё раз, чтобы добавить движки, модели или веб-кабинет | `INSTALL.bat` нет; модели добавляются из самого приложения (**Настройки → модели**) |

**Как выбрать.** Обычная рабочая машина с интернетом — берите **min**: загрузка в 40 раз меньше,
и вы поставите ровно то, что нужно вашему железу (установщик сам решит, имеет ли смысл сборка
torch под CUDA). Нет интернета, изолированный контур, раздача на флешке или просто нежелание
ставить Python в систему — берите **full**.

## Требования

Windows. Для быстрой транскрибации желателен GPU NVIDIA (runtime CUDA 12.4), но всё работает и
на CPU — медленнее.

**min** нужен Python 3.9 – 3.12 (рекомендуется 3.11). Ставить его заранее не обязательно: если
Python на машине нет, `INSTALL.bat` предложит поставить 3.11 сам — с python.org, только после
проверки подписи Python Software Foundation и только для текущего пользователя. Сборка из
Microsoft Store не подойдёт: там 3.13 и новее, а закреплённый `numpy<2.0` под них колёса не
публикует.

**full** ничего этого не требует — она везёт свой Python 3.11.

Диск: после установки min занимает примерно от 2 ГБ (CPU) до 6 ГБ (сборка torch под CUDA плюс
модель). Точную оценку установщик печатает до того, как что-либо сделает.

## Установка

**min:** распаковать → запустить `INSTALL.bat` → выбрать движки, модели и компоненты → подождать.
Затем `RUN.bat` (десктоп) или `SERVER.bat` (веб-кабинет на `http://localhost:8000`).

Веб-кабинет — отдельный пункт в списке компонентов; не нужен — не отмечайте. Без вопросов:
`INSTALL.bat --recommended --yes`. Напечатать план и ничего не ставить: `INSTALL.bat --plan-only`.

**full:** распаковать → `RUN.bat` или `SERVER.bat`.

**Из клона репозитория:** в репозитории только исходники — встроенный рантайм (6,4 ГБ) и FFmpeg
(385 МБ) в git не помещаются: GitHub отклоняет файлы больше 100 МБ, а каждый бинарник FFmpeg
весит 193 МБ. `INSTALL.bat` добирает всё недостающее, включая FFmpeg и сам Python:

```
git clone https://github.com/john7ross/meeting-summarizer.git
cd meeting-summarizer
INSTALL.bat
RUN.bat          :: или SERVER.bat для веб-кабинета
```

`RUN.bat` и `SERVER.bat` — одни и те же файлы во всех трёх случаях: интерпретатор они ищут при
запуске (встроенный рантайм → записанный `INSTALL.bat` → PATH).

## Что внутри

- **Два фронтенда на одном бэкенде** — десктопный клиент на PySide6 и многопользовательский
  веб-кабинет на FastAPI (JWT, SQLite). Набор функций одинаковый.
- **7 движков транскрибации** — OpenAI Whisper, Faster-Whisper, WhisperX, Vosk, sherpa-onnx,
  whisper.cpp, FunASR; плюс отдельно устанавливаемые community-модели (GigaAM RU, Moonshine EN).
- **Разделение по спикерам** — офлайн через sherpa-onnx без токена, опционально pyannote.
- **Анализ из 11 фич** — задачи, тональность, категория, ключевые темы, риски, цитаты,
  технологии, вопросы, рекомендации, follow-up, официальный протокол.
- **Четыре способа подключить ИИ** — локальный OpenAI-совместимый эндпоинт, облачный ключ
  (OpenAI / Anthropic / Google / xAI / Qwen / Mistral / DeepSeek), локальный агент-CLI
  (Claude Code, Codex, Hermes) или встроенный ИИ, скачиваемый по требованию.
- **Передача GPU** — на одной видеокарте резидентная LLM останавливается на время транскрибации
  и возвращается обратно.
- **Экспорт** — txt, md, json, html, pdf, docx, хранилище Obsidian, Google Sheets.
- **База знаний и поиск** — семантический поиск по архиву встреч (chromadb) плюс обычный
  текстовый поиск.
- **MCP-сервер** — архив встреч открыт AI-агенту как набор инструментов.
- **Приём материала** — файл, ссылка (включая YouTube) или запись прямо в приложении
  (микрофон **и системный звук**); длинную запись можно нарезать на отдельные встречи по волне.
- **Live-режим** — live-транскрибация и растущая live-сводка, пока встреча ещё идёт: офлайн на
  уже установленных движках и через уже настроенный способ подключения ИИ.
- **История обработки** — журнал каждого прогона (что делали, когда, сколько заняло, история
  статусов, тайминги этапов, что создано, полный текст ошибки). Лежит отдельно от очереди в
  `config/processing_history.json`, поэтому очистка очереди его не стирает.
- **Перегенерация с выбором объёма** — пересобрать только саммари, только анализ или и то и
  другое, по транскрипту, который можно поправить прямо в окне.

Подробности в [README.ru.md](https://github.com/john7ross/meeting-summarizer/blob/main/README.ru.md) и [desktop/ARCHITECTURE.ru.md](https://github.com/john7ross/meeting-summarizer/blob/main/desktop/ARCHITECTURE.ru.md).

## Что нового в 1.3.0 — live-режим

До сих пор приложение работало только с уже существующим файлом: вы записали встречу,
остановили запись и потом узнали, что в ней было. В 1.3.0 появилось то, что происходит
**во время встречи**, и то, чего не хватало самой записи.

- **Пишется и системный звук.** Микрофон снимает вас, WASAPI loopback — то, что звучит из
  динамиков, то есть остальных участников звонка. Оба идут в один WAV двумя каналами (микрофон
  слева, система справа), и в архиве остаётся весь разговор, а не ваша половина. Функция
  необязательная (пакет `soundcard`); если она недоступна, запись остаётся микрофонной и прямо
  сообщает, какая из двух причин сработала, а не пишет молча половину встречи.
- **Live-транскрибация.** Тот же PCM, что пишется в WAV, параллельно уходит в движок
  распознавания, открытый на всю встречу, и распознанные фразы появляются по мере речи — с
  пометкой MIC или SYSTEM по более громкому каналу: разделение говорящих получается бесплатно,
  из самих двух источников записи. Работает **офлайн** на уже установленных движках:
  faster-whisper, whisperx, whisper, vosk, sherpa-onnx, whisper.cpp. Для live можно выбрать
  движок и модель, отличные от основных: `medium` останется на GPU для итогового транскрипта,
  а live пойдёт малой моделью на процессоре.
- **Live-саммари.** Растущая сводка — темы, решения, задачи, открытые вопросы — обновляется
  примерно раз в 30 секунд через **тот же** способ подключения ИИ, что и итоговое саммари:
  локальный эндпоинт, облачный ключ, агент-CLI или встроенная модель. Ничего про «какой ИИ»
  не настраивается второй раз.
- **Сводка не уезжает и не пропадает.** Инкрементальное обновление строится поверх собственного
  прошлого ответа, поэтому ошибка, сделанная на третьей минуте, потом цитируется модели до конца
  встречи. На локальной модели, где токены стоят только времени, каждое обновление поэтому
  пересобирается из транскрипта; на платном облаке инкремент чередуется с периодической
  пересборкой и консолидацией, а лимит обновлений ограничивает расходы. Неудачный запрос,
  убитый процесс или нечитаемый ответ оставляют уже показанную сводку ровно на месте, а жалобу
  выносят в отдельную строку статуса.
- **Live-результаты сразу на диске** — `*_live_transcript.txt` и `*_live_summary.json` рядом с
  записью. Закрытие окна их не теряет.

- **Обработка live-встречи не транскрибирует её дважды.** После остановки диктофон предлагает
  «В обработку по live-тексту» рядом с обычным «В обработку»: live-транскрипт становится
  транскриптом встречи, и прогон сразу идёт в саммари и анализ. **Результат неотличим от любой
  другой встречи** — одна версия саммари, одна версия анализа, те же имена файлов, те же
  экспорты, заметка Obsidian и строка в Sheets. Отсутствует только этап транскрибации, потому что
  в этом прогоне он действительно не выполнялся. Другой способ попадания не должен давать иначе
  выглядящий результат, и набор тестов теперь сверяет это артефакт в артефакт с обычной встречей.
- **`live` — полноценный канал приёма** наравне с файлом и ссылкой, и всё остальное продолжает с
  ним работать. Канал хранится у встречи, помечен бейджем в очереди, назван в панели результата,
  зафиксирован в журнале обработки, попадает в лог при старте прогона, а профиль в диагностике
  показывает реально отработавшие этапы. Встречи, добавленные до этого релиза, читаются как
  `file`, а не как «неизвестно».

**Live — это черновик, и он не может ухудшить результат.** Запись всё равно проходит обычный
путь после остановки: нарезка → очередь → транскрибация → саммари → анализ, — и итоговый
транскрипт делается заново из файла выбранным движком. Отвод односторонний: PCM сначала попадает
в WAV и только потом предлагается live-воркеру, поэтому отставание, падение или выключенный
live никогда не стоят записи ни одного сэмпла.

**Ещё в этом релизе**

- Версия наконец видна в десктопном клиенте (Диагностика → Система). В футере веб-кабинета и в
  экспортируемых отчётах она была, а пользователь десктопа, сообщая о проблеме, не мог назвать
  свою сборку.
- Появился автотест, сверяющий каждое место, где версия заявлена в документации — оба бейджа
  README, оба десктопных README, обзор проекта, — с `package.json`. Раньше их не сверял никто,
  и подъём версии мог выпустить архив с именем v1.3.0, в README которого написано 1.2.1.

## Что исправлено в этой сборке

### Добавлено в пересборке 19.08.2026

- **Корректный ответ анализа мог быть отбракован как «сломанный JSON».** Перед разбором скобки
  `{}` и `[]` считались через `str.count` — то есть **вместе с теми, что стоят внутри строк**.
  Одной непарной скобки в тексте самого вопроса («п. [3», «формат { отчёта») хватало, чтобы
  нормальный ответ выглядел несбалансированным: `json.loads` не вызывался вовсе, а запуск падал
  с «AI returned invalid JSON/schema». Воспроизведено детерминированно. Теперь парсер идёт по
  ответу посимвольно, различая строковые литералы и экранирование: целый JSON разбирается как
  есть, а «ремонт» видит только то, что действительно не парсится.
- **Обрезанный ответ терял всё, что уже успел выдать.** «Ремонт» закрывал скобки в неверном
  порядке (сначала все `]`, потом все `}` — так массив объектов не закрыть) и резал хвост по
  последней запятой, а в русском тексте она почти всегда стоит внутри предложения. Замер на
  фикстуре: два готовых вопроса были, спасено ноль. Теперь сохраняются все успевшие закрыться
  элементы, отбрасывается только тот, что писался в момент обрыва.
- **Упёршийся в лимит токенов ответ выдавался за кривое форматирование модели.** `finish_reason`
  / `stop_reason` не читался ни у одного провайдера, и обрезанный ответ шёл дальше как полный.
  Теперь проверяются все четыре семейства провайдеров, и в ошибке прямо сказано, что ответ обрезан
  лимитом вывода, а не что модель испортила JSON.
- **Одна «плавающая» фича больше не стоит всей встречи.** Модель сэмплируется, а не
  детерминирована: тот же промпт, что раз вернул чистый массив, в следующий раз возвращает
  нечитаемое. Запуск обрывался на 94% — «Анализ выполнен не полностью: ошибок 1 из 11» — и уносил
  с собой заметку Obsidian и строку Google Sheets, хотя остальные десять фич отработали. Теперь у
  каждой фичи есть одна повторная попытка. Ошибки провайдера и таймауты здесь **не** ретраятся:
  у них уже есть собственный бюджет ретраев в `ai_client`. И в десктопе, и в веб-кабинете.
- **Неразобранный ответ сохраняется для диагностики.** До пользователя доходили только первые
  300 символов, остальное не хранилось нигде — после запуска нельзя было отличить обрезанный
  ответ от ответа в ограде и от обычного текста. Теперь сырой ответ пишется рядом с артефактами:
  `<встреча>_failed_<фича>.txt`.
- **Заметка Obsidian брала сегодняшнюю дату при имени файла с точками.** `Path(name).stem`
  применялся к тому, что уже было stem'ом, и `Планёрка 17.08.2026 15-33` теряла `.2026 15-33`, а
  с ним и дату. Затрагивало только имена с датой через точки; `2026-08-18 15-00-40.mkv` читался
  правильно всегда.

### В исходном релизе

- **Формальный протокол выдумывал дату.** Замер по 14 реальным анализам: в десяти стояло
  «24.10.2023», в одном — «Текущая дата (на основании транскрипции)», номер протокола каждый
  раз своего формата. При этом реальные дата и время начала лежали в имени файла
  (`2026-08-17 15-33-43.mkv`). Теперь имя разбирает один парсер (год-первым, день-первым,
  слитный и `T`-формат, с проверкой диапазонов), а дата, интервал «начало — конец» (начало плюс
  записанная длительность) и номер протокола и передаются модели, и перезаписываются поверх её
  ответа. Если в имени файла даты нет — ничего не навязывается, решает модель. Работает
  одинаково в десктопе и веб-кабинете.
- **Длинный текст ошибки заставлял окно прокручиваться вбок.** У строки статуса не было
  переноса, поэтому ошибка провайдера в три строки требовала 3783 px ширины. Теперь текст
  переносится, панель растёт в высоту, ячейка «Детали» обрезается с полным текстом в подсказке,
  а сама ошибка экранируется перед выводом в таймлайн (сообщения провайдера цитируют `<think>`
  модели, и это съедалось как разметка).
- **Отменённый прогон оставлял на диске извлечённое аудио.** Замер на одной отменённой встрече:
  328 МБ (WAV на 171 МБ плюс девять чанков). Бэкенд на ошибке удалял только полный WAV, а
  отменённый прогон убивают — он вообще не доходит до уборки. Теперь оба конца подчищают
  собственные `*_temp*.wav` этой задачи: сразу и ещё раз чуть позже.
- **Отмена пользователем писалась в лог как ошибка** — намеренное действие выглядело в
  диагностике дефектом. Теперь это запись уровня INFO, а настоящие сбои по-прежнему ERROR.
- **Успешные экспорты были не видны.** Логировались только падения, поэтому «строки в Google
  Sheets нет» и «экспорт не запускался» были неразличимы. Теперь и добавление строки, и запись
  заметок в Obsidian логируют успех.
- **Full-сборка везла мёртвую базу знаний.** Список пропускаемых каталогов в упаковщике описывает
  раскладку *этого проекта* — `config`, `logs`, `uploads`, `dist` — и применялся также к
  вендорному Python-рантайму. Совпадение по имени `logs` отрезало
  `opentelemetry/proto/collector/logs`, который OTLP-экспортёр импортирует безусловно, — и в любой
  full-сборке падал `import chromadb`. Семантический поиск и база знаний не работали вообще;
  остальное не пострадало. Теперь список действует только на наше дерево, а селфтест проверяет,
  что модуль едет. **Затронута только `full`** — `min` ставит пакеты через pip, у неё этой
  проблемы не было.
- **Фича анализа могла упасть на совершенно правильном ответе.** Парсер обрезал текст *после*
  JSON, но не *перед* ним, а модель регулярно предваряет ответ фразой («Вот JSON массив с
  извлеченными задачами:») и только потом открывает ограждение. Данные при этом были целы —
  их выбрасывало, фича возвращалась пустой, а прогон сообщал «AI returned invalid
  JSON/schema», то есть показывал пальцем на модель вместо парсера. Замерено на локальном
  Qwen и одной настоящей встрече: 2 провала из 8 прогонов одной фичи, каждый раз выбрасывалось
  девять корректных задач; после правки — 0 из 10. Парсер общий, поэтому затронуты были оба
  фронтенда.
- **Тихая запись теперь так и называется.** Файл без различимой речи раньше завершался
  «успешно» с пустым транскриптом, а недоразумение вылезало сильно позже как «No text provided».
  Теперь бэкенд сверяет транскрипт с пиковым уровнем звука и сообщает `SILENT_AUDIO` или
  `NO_SPEECH` — с локализацией в обоих фронтендах.
- **min-установки больше не отдают голые 500.** Веб-кабинет использовал зашитый путь до
  встроенного интерпретатора; теперь он ищет интерпретатор так же, как это делают лаунчеры.
- **`INSTALL.bat` ставит FFmpeg**, если его нет, — проверенной прямой загрузкой, без пакетных
  менеджеров. Повторный запуск больше не предлагает установку Python, которую уже сделал.
- **Свежий клон запускается**: `git clone` → `INSTALL.bat` → `RUN.bat`, без ручной возни с venv.
- **Адреса внутренней сети принимаются.** Веб-кабинет больше не отклоняет почту в зонах
  `.local` / `.internal` при регистрации.

## Что проверено перед релизом

- **53 селфтест-раннера, 1786 проверок** — зелено, прогон дважды подряд.

**Проверено для 1.3.0:** весь набор тестов (53 раннера, 1786 проверок, ноль падений). Два
новых раннера покрывают live сквозняком, а не через заглушки: `_selftest_live.py` (87 проверок —
нарезка потока на реплики по синтетическому PCM, схема состояния сводки, устойчивый разбор
ответа и правило «плохой ответ никогда не заменяет хорошую сводку», прогнанное через настоящий
`AIClient`) и `_selftest_live_ui.py` (100 проверок — отвод PCM, потоковый воркер через настоящий
процессный канал с настоящим офлайн-движком, стратегии обновления, лимит расходов и вся обвязка
окна записи). WASAPI loopback проверен захватом тона, который тест сам же и проиграл в
устройство вывода, а не утверждением «API не упал». Live-транскрибация прогнана на реальной
русской речи через всю цепочку и дала корректный текст: sherpa-onnx ~0,1 с на реплику на
процессоре, faster-whisper `medium` ~0,6 с на видеокарте, оба — с учётом словаря терминов.
**Не перезапускалось для этого релиза:** чистая установка в ВМ и матрица провайдеров — эти
изменения не трогают ни установщик, ни провайдеров, а live-саммари доходит до каждого провайдера
через тот же `ai_client.py`, который те тесты уже покрывают.

**Перепроверено для пересборки 19.08.2026:** весь набор тестов (51 раннер, 1581 проверка, ноль
падений); два новых раннера ровно на то, что сломалось, — `_selftest_json_recovery.py`
(11 проверок: корректный JSON «ремонт» не трогает, обрезанный ответ сохраняет все закрывшиеся
элементы) и `_selftest_analysis_retry.py` (7 проверок, сквозняком через реальный pipeline: один
нечитаемый ответ ретраится и запуск завершается зелёным, два подряд — по-прежнему падение).
Первый раннер отдельно прогнан против *прежнего* парсера и падает там на 5 проверках из 11 —
то есть он фиксирует сам дефект, а не новую реализацию. Предупреждение об обрезке проверено на
живом локальном llama.cpp с потолком вывода, принудительно выставленным в 12 токенов.
**Не перезапускалось для этой пересборки:** чистая установка на VM, матрица «каждый движок ×
каждый провайдер» и сквозной прогон базы знаний — они проверены на более ранней сборке этого же
дерева, а текущие правки не трогают ни движки, ни провайдеров, ни слой RAG.

**Перепроверено для пересборки 17.08.2026:** набор тестов дважды; документация,
C4-диаграмма компонентов и sequence-диаграмма обновлены и перерисованы; оба архива собраны из
одного замороженного дерева и просмотрены пофайлово; архив `min` распакован в чистую папку и
его `INSTALL.bat` запущен именно из этой копии (сканирование машины, русский вывод без
мойбаке, корректный вердикт).
- **Чистая установка на снапшот Windows 11 без Python** — от распаковки архива до работающего
  кабинета: установка Python, установка стека, регистрация, настоящая транскрибация, 11/11 фич
  анализа, все 12 экспортов.
- **Каждый движок транскрибации** прогнан на реальном файле; **каждый облачный провайдер** — с
  настоящими ключами; передача GPU — против живой локальной модели.
- **База знаний целиком** на рантайме в том виде, в каком он едет: документы проиндексированы,
  семантический запрос вернул нужный.
- Оба архива собраны из одного дерева, и каждый едущий файл сверен с ним побайтово: рантайм
  full-сборки совпадает с проверенным — 40 335 файлов против 40 335.

Честная оговорка: **full на чистой машине не проверялась** — 12,3 ГБ не удалось перенести в
тестовую ВМ. Проверены состав архива и то, что он собран из того же дерева, что и min-сборка,
которая полный прогон на чистой машине прошла.
