# Meeting Summarizer — Десктоп (PySide6)

[English](README.md) · **Русский**

Нативный десктоп-клиент, превращающий записи встреч в **транскрипт → саммари → расширенный
анализ**, офлайн-ориентированный и мультидвижковый. Это переписанный на PySide6 слой
интерфейса исходного Electron-приложения; проверенный Python-бэкенд переиспользуется без
изменений и управляется как CLI-подпроцессы (изоляция процессов, естественный параллелизм).

Версия 1.3.0.

## Что умеет

- **Транскрибация — 7 встроенных движков**, чтобы сравнивать и выбирать под встречу:
  OpenAI Whisper, Faster-Whisper, WhisperX (с разделением по спикерам), Vosk, sherpa-onnx,
  whisper.cpp и FunASR (SenseVoice/Paraformer, английский). RU+EN локально на всех, кроме
  FunASR (только EN). Плюс **дополнительные** community-модели (GigaAM RU, Moonshine EN),
  которые скачиваются отдельно и никогда не входят в сборку.
- **Разделение по спикерам** — по умолчанию офлайн **sherpa-onnx** (без токена, работает у
  всех сразу), опционально **pyannote** для тех, кто добавит свой HF-токен, либо выключено.
  После прогона с диаризацией спикеров можно переименовать и отредактировать реплики.
- **Саммари** — 9 AI-провайдеров (локальный/OpenAI-совместимый/Anthropic/Google/xAI/…), с явным
  **выбором модели** и модальным окном Advanced API для полностью кастомных эндпоинтов.
  **Шаблоны** промптов: 13 типов встреч × RU/EN (включая «Видео из сети» для обучающих
  роликов), у каждого — вариант с указанием спикеров, плюс собственные сохранённые шаблоны
  (правка/переименование/импорт/экспорт). Промпт по умолчанию — полный детальный оригинал.
- **Язык вывода** — саммари и анализ можно получать на языке, отличном от языка записи
  (например, английская запись → русское саммари); `outputLanguage` = auto/ru/en.
- **Добавление по ссылке** — вставьте ссылку на YouTube или файл-сервер; видео скачивается
  (yt-dlp, с автоматическим подхватом cookies браузера для входа на YouTube) и обрабатывается
  точно как загруженный файл.
- **Запись встречи и наблюдение за ней вживую** — встроенный диктофон (🎙 в шапке) пишет
  сразу в 16 кГц WAV (выбор устройства, индикатор уровня, пауза). После остановки запись
  идёт обычным путём: нарезка на фрагменты, затем очередь. Три необязательных переключателя
  — в окне записи и в Настройках → *Запись и live-режим*:
  - **Системный звук** — WASAPI loopback пишет то, что звучит из динамиков, то есть
    остальных участников звонка, вторым каналом того же WAV (микрофон слева, система
    справа). Без этого запись онлайн-встречи содержит только вашу половину. Нужен
    необязательный пакет `soundcard`; если его нет или устройство вывода не поддерживает
    захват, запись остаётся микрофонной и сообщает, что именно из двух.
  - **Live-транскрибация** — PCM, идущий в WAV, параллельно уходит в движок распознавания,
    открытый на всю встречу (`backend/live_stt.py`), и фразы появляются в панели по мере
    речи, с пометкой MIC/SYSTEM по более громкому каналу. Офлайн, на уже установленных
    движках: `faster-whisper`, `whisperx`, `whisper`, `vosk`, `sherpa-onnx`, `whisper-cpp`.
    Для live можно выбрать движок и модель, отличные от основных.
  - **Live-саммари** — растущая сводка (темы, решения, задачи, открытые вопросы),
    обновляется примерно раз в 30 с через `backend/live_summary.py` тем же способом
    подключения ИИ, что и итоговое саммари. На локальной модели каждое обновление
    пересобирается из транскрипта (ошибка не закрепляется), на платном облаке —
    инкремент с периодической пересборкой, а `liveSummaryMaxUpdates` ограничивает расходы.
    Неудачное или нечитаемое обновление никогда не стирает уже показанную сводку.

  Оба live-результата пишутся рядом с записью по мере поступления
  (`*_live_transcript.txt`, `*_live_summary.json`). Это **черновик**: если не попросить иначе,
  итоговый транскрипт всё равно делается заново из файла выбранным движком, поэтому live может
  отставать или падать, не влияя на результат.
- **Обработать live-встречу, не транскрибируя её дважды** — после остановки диктофон предлагает
  «В обработку по live-тексту» рядом с обычным «В обработку». Live-транскрипт кладётся в папку
  встречи под стандартным именем `<stem>_raw.txt`, и по нему идут саммари → анализ.
  **Набор артефактов такой же, как у любой другой встречи**: одна версия саммари, одна версия
  анализа, те же имена, те же экспорты, заметка Obsidian и строка в Sheets. Отсутствует только
  этап транскрибации — потому что в этом прогоне он действительно не выполнялся (это же видно и
  в профиле обработки). Нарезка для этого пути пропускается: live-транскрипт покрывает всю
  запись, и разрезав аудио, вы получили бы в каждом фрагменте текст всех остальных.
- **`live` — полноценный канал приёма** наравне с файлом и ссылкой. Он хранится в записи истории
  (`source`), показывается бейджем `● live` в строке очереди, назван в панели результата
  («Источник: Live-встреча»), фиксируется в журнале обработки (своя колонка в окне 🕘) и пишется
  в лог при старте прогона. Встречи, добавленные до этого релиза, и все файловые встречи
  читаются как `file` — никогда как «неизвестно».
- **Встроенный локальный ИИ (опция, качается по требованию)** — пользователь без своей
  нейросети может попросить приложение скачать актуальную сборку сервера llama.cpp
  (резолвится вживую через GitHub Releases API, CUDA или CPU) и подобранную по объёму
  видеопамяти свежую GGUF-модель (Qwen3 / Gemma 3), либо любую свою по ссылке, запустить её на порту 8081 (чтобы не тронуть чужую модель
  на 8080) и переключиться на неё. В дистрибутив это **не входит** — попадает в
  `resources/local_ai/` только по запросу. Настройки → AI-провайдер → «Встроенный локальный ИИ».
- **MCP-сервер — архив встреч как инструменты для агента** (`backend/mcp_server.py`).
  Обратное направление: не мы отдаём транскрипт, а агент (Claude Code, Codex, Hermes…) сам
  ходит в архив. Инструменты: `list_meetings`, `get_transcript`, `get_summary`,
  `get_analysis` (целиком или одна фича), `search_transcripts` (буквальный) и
  `search_knowledge` (семантический RAG). Stdio JSON-RPC без зависимостей — SDK не нужен.
  MCP ищет сразу по всем локальным desktop/server/shared-каталогам. В настройках RAG можно
  оставить изолированную базу (по умолчанию) либо подключить desktop и server-аккаунт в
  одной установке к общей базе по сгенерированному секретному коду.
  Команды подключения: `backend\python\python.exe backend\mcp_server.py --print-registration`.
  Подробности — [docs/MCP_USAGE.ru.md](../docs/MCP_USAGE.ru.md).
- **Локальные агент-CLI как AI-провайдер** — кроме HTTP-эндпоинтов и облачных ключей, проходы
  саммари и анализа можно отдать уже установленному на машине агенту: **Claude Code**
  (`claude -p {prompt}`), **Codex** (`codex exec {prompt}`), **Gemini CLI**, **Hermes** или
  любой команде, читающей stdin и печатающей ответ. Транскрипт передаётся через **stdin**
  (встреча на 80 тыс. символов не влезет в аргумент командной строки), промпт подставляется
  вместо `{prompt}`, а для агентов, которым удобнее файлы, есть `{prompt_file}` и
  `{text_file}`. Ключи и выбор модели остаются в конфиге самого агента.
- **Нарезка одной записи на фрагменты по встречам** — когда в файле несколько встреч подряд,
  окно добавления предлагает предпросмотр с плеером и перетаскиваемой шкалой: отметьте начало
  и конец каждой встречи, и каждый фрагмент будет вырезан (ffmpeg, 16 кГц моно) и поставлен в
  очередь **отдельной задачей** со своим транскриптом, саммари и анализом — вместо одного
  смешанного саммари. «Обработать файл целиком» пропускает нарезку.
- **Расширенный анализ** — 11 фич (задачи, тональность, категория, риски, цитаты, технологии,
  открытые вопросы, рекомендации, вопросы к следующей встрече, ключевые темы, формальный
  протокол ГОСТ/ISO), отрисованные панелями; каждая фича включается отдельно. Источник
  настраивается: по полному транскрипту (по умолчанию, максимальная полнота) или по саммари
  (быстрее, но менее полно). Чанкинг также выключен по умолчанию и включается только как
  явный компромисс для моделей, которым не хватает контекстного окна. Дата, время начала и
  окончания и номер формального протокола берутся из имени файла записи
  (`2026-08-17 15-33-43.mkv`), а не из фантазии модели; если даты в имени нет — решает модель.
- **Контекстная память** (по желанию, строго в рамках проекта) — подмешивает саммари прошлых
  встреч *того же* проекта в промпт, чтобы сохранялась связность между встречами.
- **Экспорт** — txt/md/json/html/pdf/docx (без потери данных), хранилище Obsidian, файлы по
  спикерам и Google Sheets (через развёрнутый пользователем webhook Apps Script). Анализ в
  HTML — карточный отчёт с бейджами приоритетов и полосами тональности.
- **Знания** — настоящий семантический RAG (chromadb, офлайн-эмбеддинги по умолчанию) плюс
  текстовый поиск по транскриптам.
- **Эксплуатация** — история версий и **перегенерация с выбором объёма** (только саммари /
  только анализ / саммари + анализ, чтобы прогон, упавший на одном разделе анализа, не
  пересобирал заодно и саммари), окно **История обработки** (🕘) — журнал каждого прогона: что
  делали, когда начали, сколько заняло, история статусов, тайминги этапов, что создано и полный
  текст ошибки; лежит в `config/processing_history.json` отдельно от очереди, поэтому удаление
  встречи из таблицы его не стирает. Плюс автоопределение CUDA с откатом на CPU, окно
  Диагностики (метрики системы, профиль обработки диаграммой Ганта, A-B сравнение движков,
  логи) и окно статистики.

## Требования

- **Встроенный Python 3.11** в `backend/python/python.exe` (приложение использует именно его,
  а не системный). `ffmpeg` (находится через `paths.py`) для извлечения аудио. CUDA
  необязательна — определяется автоматически, с откатом на CPU.
- Установка зависимостей во встроенный рантайм:
  ```
  # сначала torch, из индекса CUDA 12.4 (только CPU: используйте индекс PyTorch CPU):
  backend\python\python.exe -m pip install torch==2.6.0+cu124 torchaudio==2.6.0+cu124 \
      torchvision==0.21.0+cu124 --index-url https://download.pytorch.org/whl/cu124
  backend\python\python.exe -m pip install -r desktop\requirements.txt
  ```
  Разделение обязательных и опциональных зависимостей, а также не-пакетные ресурсы (ffmpeg,
  модели движков) описаны в [requirements.txt](requirements.txt).

## Запуск

```
backend\python\python.exe desktop\run.py
```

Или двойным кликом по `RUN.bat` в корне репозитория (без окна консоли).

Модели движков скачиваются по требованию из Настроек (или командой
`backend/models_cli.py download …`) в `resources/<движок>_models/`. Конфигурация лежит в
`config/settings.json`.

## Быстрая проверка (self-tests)

Порт содержит настоящие запускаемые smoke-тесты (без сети) — запустите любой или весь набор:

```
set QT_QPA_PLATFORM=offscreen
backend\python\python.exe desktop\_selftest_pipeline.py      # полный цикл транскрипт→саммари→анализ
backend\python\python.exe desktop\_selftest_settings.py      # загрузка/видимость/сохранение настроек
backend\python\python.exe desktop\_selftest_engines.py       # реестр движков
backend\python\python.exe desktop\_selftest_mcp.py           # MCP-сервер по реальному протоколу
...                                                          # всего 41 набор в desktop (+2 в server/);
                                                             # каждый печатает SUMMARY ALL_PASS и возвращает ненулевой код при падении
```

Живые проверки движков (нужна модель на диске) — скрипты `desktop/_livetest_*.py`.
